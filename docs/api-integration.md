# API Integration

## Alarm Management API

Candidate-built FastAPI simulator (`simulator/`), backed by the Postman collections in `postman/` and a seeded SQLite database (`test-data/*.json`, loaded once on startup). Full surface:

| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Liveness check (used by Docker Compose healthcheck) |
| `/assets/search` | GET | Search assets by name substring, optional `unit` filter |
| `/assets/{asset_id}/metadata` | GET | Full asset metadata (manufacturer, install date, criticality) |
| `/alarms` | GET | List alarms, filterable by `asset_id`/`site`/`status`, paginated, sortable |
| `/alarms/{alarm_id}` | GET | Single alarm by ID |
| `/alarms/summary` | POST | Group + aggregate alarms into KPI values |
| `/alarms/trends` | POST | Bucket alarms over time, compute per-bucket metrics |
| `/alarms/correlation` | POST | Alarm-name pairs that co-occur within a lag window |
| `/alarms/flood-analysis` | POST | Rolling-window alarm burst detection |
| `/alarms/rationalization-candidates` | POST | Flag recurring/chronically-stale alarm+asset pairs |
| `/alarms/priority-score` | POST | 0–100 urgency score for one alarm |
| `/analytics/kpi-definitions` | GET | List all known KPI definitions |
| `/recommendations/operator-actions` | POST | Playbook actions for an alarm |
| `/calculation-code/generate` | POST | Register a new ad-hoc KPI calculation |
| `/calculation-code/execute` | POST | Run a previously generated calculation |

Full request/response schemas are documented per-tool in `docs/mcp-tool-catalog.md` (the MCP tool layer is a thin, typed wrapper directly over this API — one tool per endpoint, same fields).

## Authentication

Bearer token, same shared secret on both sides:

- Simulator: every route (except `/health`) depends on `require_bearer_token` (`simulator/app/auth.py`), which checks the `Authorization: Bearer <token>` header against `ALARM_API_TOKEN`. A missing/malformed header or wrong token → `401`.
- MCP server: `AlarmManagementClient` (`mcp-servers/alarm-management/client.py`) holds the same `ALARM_API_TOKEN` and attaches it to every outbound request. The token is never logged (the client logs individual fields, never the `headers` dict) and never returned in any tool response.

## Trace / Correlation Metadata Propagation

Three headers, read via a shared FastAPI dependency (`simulator/app/tracing.py::get_trace_context`) on the endpoints tagged "(trace headers)" in the base Postman collection — summary, correlation, recommendations, execute-calculation:

- `trace_id` — generated by `AlarmManagementClient.request()` if the caller didn't supply one (`mcp-{8 random hex chars}`), sent on **every** request (not just the tagged ones), and echoed back on the response's `trace_id` header.
- `x-client-id`, `x-metadata-tag` — optional, forwarded through if the MCP tool call supplies them.

All three are logged server-side (`trace_context` log event) for correlation across the simulator, the MCP server, and the copilot backend's own audit trail.

## Pagination

`/alarms` (and the ticketing API's `/tickets`) share the same shape: `page` (1-indexed), `page_size`, plus a `PaginationMeta` response block (`page`, `page_size`, `total_items`, `total_pages`). `/alarms` also supports `sort_by` (`start_time`/`severity`/`status`/`alarm_name`) and `sort_order`.

## Ticketing API Integration

Candidate-built mock ticketing API (`ticketing/`), not a real Jira/Azure DevOps/ServiceNow/GitHub Issues integration — chosen to keep the assignment's time box focused on the MCP+RAG integration pattern rather than a third-party API's auth/rate-limit specifics. Same auth pattern as the Alarm Management API (bearer token via `TICKETING_API_TOKEN`). Endpoints:

| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Liveness check |
| `/tickets/search` | GET | Keyword search by summary/description/labels, ranked by word-overlap score |
| `/tickets` | GET | List tickets, filterable by `asset_id`(s)/`status`, paginated |
| `/tickets/{ticket_id}` | GET | Single ticket by ID |
| `/tickets` | POST | Create a ticket — **write operation, gated behind GUI confirmation** |
| `/tickets/{ticket_id}` | PATCH | Update a ticket's status/resolution_notes/labels/priority — **write operation, gated behind GUI confirmation** |

`POST /tickets` is idempotent per `alarm_id`: if a non-closed ticket already exists for the given `alarm_id`, that existing ticket is returned instead of creating a duplicate.

## Multi-Step API Chaining

The MCP client orchestration layer (`apps/backend/graph/`) chains multiple Alarm Management/Ticketing calls within a single conversational turn by re-planning after every tool result (see `docs/architecture.md`'s Request Flow). The reference chaining scenario used for both design and the automated end-to-end test is **CHAIN-09** from `postman/chaining/Alarm-API-Chaining.postman_collection.json` ("East Active → Priority → Recommendation"):

1. `GET /alarms?site=EastRefinery&status=active` → pick the first `alarm_id`
2. `GET /alarms/{alarm_id}` → alarm detail
3. `POST /alarms/priority-score` `{alarm_id}` → priority score
4. `POST /recommendations/operator-actions` `{alarm_id}` → recommendations

Automated coverage: `tests/e2e/test_chain09_orchestration.py` runs this exact sequence in-process against the real simulator app and the real alarm-management MCP server (no mocking).
